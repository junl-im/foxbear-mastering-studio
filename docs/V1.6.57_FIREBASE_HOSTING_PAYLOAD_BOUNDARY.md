# v1.6.57 Firebase Hosting Payload Boundary

## 문제

- Firebase Hosting의 `public`이 저장소 루트 `.`를 가리켜 ignore 규칙 하나가 빠지면 개발·운영 파일이 공개될 수 있었다.
- 로컬 Firebase 캐시에는 `.git` 객체가 5천여 개 기록돼 있었지만 기존 `hosting:check`는 실행 파일 확장자만 검사했다.
- 직접 `firebase deploy`를 실행하면 별도의 공개 디렉터리 생성 계약이 없어 배포 경계를 강제할 수 없었다.

## 수정

- Hosting 공개 루트를 `dist/hosting`으로 변경했다.
- `tools/stage-hosting-payload.js`가 공개 루트 파일 8개와 `assets/`, `src/`, `vendor/`만 복사한다.
- 공개 트리 안의 숨김 파일, 개인키·환경파일 계열, Windows 실행 파일, 심볼릭 링크를 거부한다.
- `tools/check-hosting-payload.js`가 Firebase 설정, predeploy 훅, 생성 manifest, 허용 경로를 함께 검증한다.
- Firebase Hosting `predeploy`에 `npm run hosting:check`를 연결해 직접 배포도 동일한 검사를 통과해야 한다.
- `.firebase/`를 Git에서 제외하고 기존 Hosting 캐시 추적 파일을 제거했다.

## 검증 계약

- `firebase.json`의 Hosting public은 정확히 `dist/hosting`이어야 한다.
- Hosting predeploy는 `npm run hosting:check`를 실행해야 한다.
- 생성 payload에는 지정된 루트 파일과 `assets/`, `src/`, `vendor/`만 존재해야 한다.
- `.git`, `.firebase`, `functions`, `qa`, `tools`, `docs`, package metadata, 환경파일, 키 파일, 실행 파일은 payload에 존재할 수 없다.
- `qa/v1657_hosting_payload_boundary_hardening_smoke.js`는 합성 저장소와 실제 프로젝트 payload를 모두 검증한다.

## 운영 적용

1. 덮어쓰기 ZIP을 저장소 루트에 적용한다.
2. Git에서 `.firebase/hosting..cache` 삭제가 반영됐는지 확인한다.
3. `npm run check:release`를 실행한다.
4. `npm run deploy:spark` 또는 `npm run deploy:incident`를 실행한다.
5. 배포 로그에서 Hosting predeploy와 150개 허용 파일 staging 결과를 확인한다.

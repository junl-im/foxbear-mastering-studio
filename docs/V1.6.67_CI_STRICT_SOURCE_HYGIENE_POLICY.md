# v1.6.67 CI Strict Source Hygiene Policy

## Problem

v1.6.66 repaired known local/generated files inside the GitHub Actions workspace before validation. That recovered an interrupted extract-overwrite patch, but it could also let the workflow pass while the repository still tracked `.firebaserc`, `.firebase/`, or generated QA output.

A release gate must distinguish two contexts:

- Local GitHub Desktop/package preparation may remove an explicit allowlist of generated state and expose the deletions for review.
- GitHub Actions must never mutate away committed violations before validation.

## Applied policy

- `tools/run-source-hygiene-gate.js` selects strict mode when `GITHUB_ACTIONS=true` or `FOXBEAR_SOURCE_HYGIENE_MODE=strict`.
- Strict mode runs only `check-source-hygiene.js` and leaves every offending path in place.
- Local mode runs the narrow repair allowlist and immediately follows it with the strict check.
- Direct `repair-source-hygiene.js` execution is refused in GitHub Actions unless an explicit emergency override is set.
- Both Pages workflows run strict source hygiene before `npm ci`, preventing dependency installation from preceding repository hygiene validation.
- CI failures emit GitHub file annotations and exact local remediation commands.
- Delivery ZIP creation keeps local repair followed by strict archive validation.

## Verification

The dedicated regression creates committed local Firebase state and verifies:

1. CI strict mode fails.
2. The offending file remains present.
3. A GitHub file annotation and remediation command are printed.
4. Local repair mode removes only allowlisted generated/local state and then passes.
5. Secret-like `.env*` files are never auto-deleted and continue to fail.

## Problems confirmed

### 1. Invalid CORP response-header value

`firebase.json` assigned `same-origin-allow-popups` to both COOP and CORP. The value is valid for `Cross-Origin-Opener-Policy`, but not for `Cross-Origin-Resource-Policy`. A browser can ignore an invalid CORP value, leaving the intended resource policy unenforced.

**Resolution**

- Keep COOP as `same-origin-allow-popups` so Google popup authentication continues to work.
- Change CORP to the valid restrictive value `same-origin`.
- Add a regression that rejects any CORP value containing `allow-popups`.

### 2. Anonymous access to SMTP deployment verification

`checkIncidentDeploymentReadiness` accepted any authenticated Firebase identity, including anonymous accounts, and always read the Gmail Secret and called SMTP `verify()`. Its cooldown document was keyed by UID, so a caller could create another anonymous UID and bypass the previous UID's cooldown.

**Resolution**

- Public/anonymous scope checks only Callable Functions and Firestore.
- Gmail Secret and SMTP connection checks are returned as successful-but-restricted placeholders and do not instantiate Nodemailer.
- Full SMTP checks require all of the following: Firebase-authenticated UID, `google.com` sign-in provider, verified email, active non-expired `siteAdmins/{uid}` authorization, and matching optional administrator email/provider fields.
- Readiness cache IDs are fixed to `public` and `admin`, not caller UID.
- Same-instance concurrent checks are coalesced by scope.
- Callable scaling is bounded with `maxInstances: 2`.
- The client renders restricted checks as warnings and labels a public result `기본 정상`, avoiding a misleading all-green SMTP result.

## Compatibility and exception review

- Anonymous incident reporting remains enabled; only sensitive deployment diagnostics are restricted.
- Public readiness still returns a complete boolean contract, preserving existing client flow and local history.
- A restricted SMTP row is intentionally `ok: true` plus `status: restricted`; this means the basic deployment check can complete without falsely claiming the SMTP path was tested.
- Administrator checks use a separate cache so a recent public check never masks an administrator SMTP check.
- Administrator results are shared among authorized administrators for the cooldown window; no secret value, password, or token is returned or cached.
- App Check remains disabled according to the project's existing policy. Scope-based caching and verified administrator authorization reduce the concrete abuse path without changing that policy.
- Cross-instance requests can still overlap up to the bounded instance count. A future Firestore transaction lease can reduce that final concurrency window.
- Real SMTP, Firebase Auth, Firestore Rules, and deployed Hosting headers still require production verification after deployment.

## Repeated challenge questions and answers

1. **Does public readiness still work without administrator login?** Yes. Functions, Firestore, CSP, version, cache, and timestamps remain available.
2. **Does a public request read the Gmail Secret?** No.
3. **Does a public request create a Nodemailer transport?** No.
4. **Can changing anonymous UID bypass the cooldown?** No. All public callers share the `public` cache document.
5. **Can changing Google UID bypass the public cooldown?** A non-admin Google user still receives the shared public result.
6. **Can an anonymous token claim an administrator UID?** No. The provider must be `google.com`, the email must be verified, and `siteAdmins/{uid}` must be active.
7. **Can an unverified Google account run SMTP verification?** No.
8. **Can a verified Google account without a site-admin document run it?** No.
9. **Can an expired site-admin document run it?** No.
10. **Can the public cache hide an SMTP failure from an administrator?** No. Public and administrator caches are separate.
11. **Can the administrator cache reveal the Gmail password?** No. Only normalized status, code, reason, and message fields are returned.
12. **Can a public caller infer whether the Secret exists?** No. Both sensitive rows return the same administrator-required state.
13. **Does `ok: true` on a restricted row mean SMTP was tested?** No. `restricted: true`, `status: restricted`, scope, UI warning, and summary label make the distinction explicit.
14. **Would setting restricted rows to `ok: false` be clearer?** It would break the basic public readiness contract and turn every normal public check into a deployment failure. The explicit restricted flag is safer and backward-compatible.
15. **Could a cached result be malformed?** The existing completeness check still requires product version, Functions origin, and boolean results for every server check.
16. **Could an old per-UID cache be reused?** No. v1.6.59 reads only fixed `public` or `admin` document IDs.
17. **Could many simultaneous public calls all run Firestore checks?** Same-instance calls are coalesced. Cross-instance overlap is bounded by `maxInstances: 2`.
18. **Why not require App Check immediately?** The project explicitly removed App Check and supports external/static hosting. Reintroducing it requires production keys, CSP, and hosting-origin acceptance work outside this patch.
19. **Why keep the Secret bound to the Callable?** The administrator branch still performs the real SMTP check; Firebase requires the secret binding for that branch.
20. **Does the header change break Google login popups?** No. COOP remains `same-origin-allow-popups`; only CORP changes to `same-origin`.
21. **Could strict CORP block same-origin static assets?** No. The site's own assets are same-origin.
22. **Could strict CORP affect intentionally embedded cross-origin resources?** CORP is sent by this Hosting origin for its own resources. Production smoke testing should still cover any externally embedded FoxBear asset use.
23. **Are Firestore Rules changed?** No. Callable Admin SDK access is governed server-side, while existing client Rules remain unchanged.
24. **Is administrator authorization based only on a client-supplied email?** No. Callable auth tokens are validated by Firebase before handler execution, and the UID must map to an active admin document.
25. **Can two administrators trigger two checks inside one minute?** They share the administrator cache, so sequential calls do not. A narrow cross-instance simultaneous race remains a future transaction-lease improvement.
26. **Does cache write failure expose SMTP to public users?** No. Access scope is determined before inspection; public inspection never enters the SMTP branch.
27. **Does cache read failure cause a public SMTP check?** No. It causes a fresh public basic check only.
28. **Does a stale client-local result hide the new restricted state?** The normal cooldown can retain the previous local result until its next-check time; version/cache revision invalidation and a subsequent check replace it.
29. **Does the service worker cache revision change?** Yes. v1.6.59 uses a new synchronized cache generation.
30. **What remains unverified locally?** Live Firebase deployment, real Google administrator token flow, real Secret access, real Gmail SMTP connectivity, and browser automation requiring Playwright/Chromium.

# v1.6.27 Incident Multi-Tab Queue Ownership Safety

## Scope

This patch audits the local anonymous incident queue when multiple FoxBear tabs share the same browser profile. It covers queue persistence, cross-tab synchronization, recovery ownership, stale flush commits, storage migration, bounded diagnostics, and lifecycle cleanup. Audio DSP, mastering targets, encoders, Firebase document schemas, SMTP content, and report payload contents are unchanged.

## Problems found

1. The v1.6.26 conflict-safe commit protected reports appended during a flush in one tab, but two tabs could still read the same localStorage array and overwrite each other's enqueue operation.
2. `state.flushing` was tab-local. Two tabs could therefore flush the same snapshot at the same time and submit duplicate reports.
3. A delivered fingerprint alone was not a durable cross-tab commit identity. A stale shard could restore a previously delivered occurrence, while a permanent fingerprint tombstone would incorrectly suppress a later report of the same issue.
4. Peer queue changes were not reflected in the open diagnostic UI until another local render trigger occurred.

## Implementation

- Added `src/boot/incident-queue-coordination-service.js`.
- Each tab writes to its own bounded queue shard, so unrelated tab writes never replace one shared array.
- Reads merge the legacy queue and all visible shards, sort by report timestamp, deduplicate by fingerprint, and enforce the existing eight-item and 96 KiB limits.
- Successful commits use an exact occurrence identity composed from fingerprint and client timestamp. Bounded tombstones protect against stale shard resurrection without permanently blocking a later occurrence of the same fingerprint.
- Flush execution uses the Web Locks API when available. Browsers without Web Locks use a short renewable localStorage lease with ownership verification and bounded contention diagnostics.
- `incident-reporter.js` now acquires cross-tab ownership before delivery, checks ownership before and after each network submission, and commits delivered entries by exact occurrence.
- BroadcastChannel and storage-revision notifications update peer queue counts and compact delivered entries from the current tab shard.
- Legacy single-key queues remain readable and are removed through the coordinated commit path.

## Privacy and safety contracts

- Cross-tab diagnostics expose counts, lock mode, contention totals, shard totals, and timestamps only.
- Tab identifiers remain internal and are not rendered in user-facing status text.
- Report messages, stack traces, filenames, audio, tokens, Firebase credentials, SMTP Secrets, IP addresses, SSIDs, and location data are not added to coordination metadata.
- Queue capacity remains globally bounded at eight visible reports.

## Regression coverage

`qa/v1627_incident_multitab_queue_ownership_stress_smoke.js` verifies:

- independent tab shards preserve both writes;
- duplicate fingerprints merge to one visible occurrence;
- a 60-write two-tab storm retains the newest eight reports;
- reports queued after a flush snapshot survive its commit;
- exact tombstones allow a later occurrence of the same fingerprint;
- 50 simultaneous peer ownership attempts cannot start a second delivery loop;
- ownership becomes available immediately after release;
- legacy queue migration, script order, service-worker caching, reporter wiring, and handoff package requirements.

## Remaining environment gates

- Full Playwright execution requires an installed Chromium runtime.
- Production validation still requires Firebase Hosting, Functions, Firestore, App Check, and Gmail SMTP to be deployed together.
- Real browser crash recovery and device-level background eviction should be verified on Chrome, Safari, and Android WebView because storage-event and Web Locks availability vary by engine.
## Final verification

- Cumulative static and behavioral regression suite: `364/364` passed.
- Browser fixture preflight, Firebase Functions syntax, version/SRI synchronization, dependency metadata, handoff state, engine bench, and golden-audio checks passed.
- Golden fixtures remained at `-14.00 LUFS`; measured fixture peaks stayed between `-9.62` and `-5.64 dBTP`, and the peak-stress contract remained `-1.00 dBTP`.
- Dependency health reported only the five expected sandbox installation warnings for Playwright and Functions runtime packages.
- Full installed-browser execution was not claimed: the sandbox lacks a usable Playwright/Chromium runtime, so real browser multi-tab behavior remains a deployment-environment gate.

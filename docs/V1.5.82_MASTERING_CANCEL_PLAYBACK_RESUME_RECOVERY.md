# v1.5.82 Mastering Cancellation and Foreground Playback Recovery

## Problem

Quality-gate automatic recovery caught every error and preserved the first render. A batch cancellation or current-track skip during the safe re-render could therefore be converted into a normal recovery failure and the already encoded first render could continue to final commit. Separately, mobile browsers can reject the first media `play()` immediately after a screen-lock, call, or app-switch return with a transient `AbortError` even after the user taps play.

## Fix

- Cancellation and worker abort errors restore first-render track state and are rethrown to the parent mastering job.
- Cancelled recovery is marked `cancelled`, does not emit an operational-failure incident, and cannot proceed to Blob commit.
- Playback starts immediately in the user activation task, then retries once only for recoverable interruptions after the audio graph resume promise settles.
- Request generation, connection state, and media readiness are checked before retry.
- Direct local-waveform and A/B fallback `play()` calls use the shared transition service.

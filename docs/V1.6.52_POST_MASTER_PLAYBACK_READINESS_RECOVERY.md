# v1.6.52 Post-Master Playback Readiness Recovery

## Audit findings

Intermittent playback failure after mastering was traced to three independent race conditions:

1. The 100% completion render already committed the mastered Dock player, but a later `master-complete` repair forcibly invalidated and rebuilt it. A fast Play tap could therefore target a player that was removed before the browser completed `HTMLMediaElement.play()`.
2. The shared playback path selected the first Dock player child. During crossfade cleanup that child could be stale while another audio element was the real active source.
3. A cancelled fade or crossfade could leave a still-playing element at a near-zero transitional volume, producing a successful play state with no audible output.

Mobile and in-app browsers added two smaller failure modes: Blob media metadata can arrive later than the original readiness window, and a completed or errored media element may need a fresh `load()` and user-gesture retry.

## Patch

### Stable completion commit

- The 100% mastering render is now the single player commit.
- Post-master stabilization verifies selected track, playback mode, Blob URL, player ownership, and generation before repairing anything.
- A valid connected mastered player is preserved instead of being rebuilt.
- Deferred repair is generation-fenced so a later track or source cannot be modified by an older callback.

### Active-player ownership

- Playback starts from the currently active audio element returned by the Dock state.
- The owning player is resolved from that audio element rather than `firstElementChild`.
- Detached or replaced targets are re-resolved once before the request is considered failed.
- External playback controls receive a boolean result and can report a real failed start rather than silently doing nothing.

### Blob readiness and replay recovery

- Mastered and highlight media use `preload="auto"`.
- Recoverable readiness is bounded to 2.2 seconds for delayed Blob metadata in mobile and in-app browsers.
- Ended media rewinds before replay.
- Fresh Blob sources and errored media receive a controlled `load()` before the user-gesture play attempt.
- `loadedmetadata`, `canplay`, and `error` handlers keep the control state recoverable without permanently disabling Play.

### Audible transition recovery

- If a play fade is cancelled while it still owns the connected audio element, the remembered target volume is restored.
- If either side of a crossfade is cancelled, both elements recover their intended target volumes before the transition exits.
- Existing generation fencing remains in place so an older transition cannot overwrite a newer request.

### Module boundary

The recovery controller is isolated in `src/audio/post-master-playback-recovery-service.js`. This keeps `src/app.js` below the historical line-budget contract while allowing the readiness and ownership rules to be tested independently.

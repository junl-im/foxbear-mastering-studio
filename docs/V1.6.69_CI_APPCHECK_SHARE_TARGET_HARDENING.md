# v1.6.69 CI, App Check Policy, and Share Target Hardening

## Why this patch exists

Three small reliability gaps remained after v1.6.68:

1. The Pages browser job could install Chromium and execute while the static release gate was already failing in parallel.
2. The intentional no-App-Check policy was repeated as literals across Callable options and status metadata, allowing partial policy drift and always reporting the token as absent.
3. PWA share-target payloads were written to IndexedDB before validating type or size, and abandoned records had no retention bound.

## Applied controls

- `browser-qa` now depends on `static-qa` in the primary Pages workflow.
- `functions/app-check-policy.js` owns the immutable Callable policy, option construction, and request token-observation metadata.
- All five public Callable Functions use `incidentCallableOptions(...)`; direct `enforceAppCheck` literals are forbidden by regression coverage.
- The browser runtime exposes one frozen `APP_CHECK_POLICY` object used by Firebase and incident diagnostics.
- The share target accepts only supported audio/container formats, up to 220 MiB per file, 512 MiB total, and 12 accepted files.
- Share records expire after 24 hours and the store retains at most eight records. Cleanup uses keys only, avoiding loading large Blob values during pruning.
- Share launch and error query parameters are removed after success, expiry, unsupported input, or storage failure.

## Deployment note

App Check remains intentionally disabled for this release. This patch prevents accidental partial enforcement and improves observability; it does not initialize the App Check client SDK or add reCAPTCHA dependencies.

# v1.6.108 Mastering Progress Visibility Hardening

## Goal

Make mastering visibly active at one-percent resolution without increasing heavy application re-render frequency or changing DSP output.

## Why mastering looked paused

- The floating mastering HUD rounded progress to 5% steps.
- Pitch-worker progress changed the report text but did not advance the overall track progress.
- Offline master-chain rendering had no native intermediate progress signal between the 65% and 80% checkpoints.
- Finalizer/encoder worker progress scheduled broad application renders as often as every 80ms, so simply increasing update frequency would have risked making the UI heavier.

## Changes

- The floating mastering HUD now displays monotonic **1%** progress and never rounds to 100% before completion.
- Lightweight progress ticks update the mastering HUD / bulk HUD directly; full `renderAll()` work stays on **5%** checkpoints and is deduplicated.
- Decode and offline master-chain stages use bounded activity heartbeats that stop below the next real checkpoint (`9%` and `79%`). They communicate liveness without claiming completion of the next stage.
- Pitch worker progress is mapped into overall mastering progress **40–54%**.
- Finalizer worker progress maps into **90–94%** and encoder progress into **95–99%**.
- The master-chain completion path yields once before the synchronous safety scan so the browser can paint the latest progress state first.

## Performance / audio impact

- No mastering EQ, dynamics, limiter, loudness, pitch, encoder, or quality-gate DSP math changed.
- Broad application rendering is not increased to one-percent frequency; only the small progress surfaces update at that cadence.
- `src/app.js` remains below the existing 13,250-line architecture gate.

# v1.6.70 Atomic Share Retry, Policy Drift Diagnostics, and CI Efficiency

## Problem review

The v1.6.69 share-target service removed its IndexedDB handoff record before the asynchronous application import pipeline completed. A transient import exception could therefore be reported as success or permanently lose the only retryable copy. Record-count retention also allowed up to eight very large shares, which could exceed practical browser storage quotas.

The manual `gh-pages` fallback workflow installed Chromium before Static release gate, and browser impact normalization did not ignore current full/patch ZIP verifier paths during pure version bumps. Incident diagnostics showed App Check enforcement/token state but did not warn when the deployed Functions policy contract differed from the client.

## Changes

- Read the share record without consuming it.
- Await `handleFiles()` and use its actual `added` result.
- Delete the record only after successful import or a terminal unsupported, expired, or device-limit outcome.
- Preserve the record and launch query after transient exceptions for reload retry.
- Wait for IndexedDB transaction completion and handle blocked/version-change conditions.
- Add a 768 MiB aggregate share-store budget in addition to TTL and record-count limits.
- Cap share title, text, and URL metadata.
- Warn on App Check policy version, mode, or reason drift.
- Run fallback Static release gate before browser scope and Chromium installation.
- Normalize `package:verify:full` and `package:verify:patch` as release metadata.

## Verification

- Dedicated dynamic IndexedDB/import retry regression.
- Share-retention byte-budget planning regression.
- App Check drift diagnostics regression.
- Fallback workflow ordering regression.
- Version-only browser-impact normalization regression.
- Full static/behavioral suite and release boundary checks.

# v1.6.75 Download Progress Visibility and Admission Fallback Closure

## Problem 1: encoding progress below the visible fold

The download sheet accumulated format, filename, recovery, and action controls over time. On shorter viewports the worker encoding card could exist below the initially visible area, while the mobile action footer remained sticky.

### Fix

- Desktop maximum dialog height increases to `min(92dvh, 840px)`.
- Mobile sheet can use `min(98dvh, 920px)` while remaining bounded by the visual viewport safe area.
- The worker progress card is mounted before filename controls while hidden at idle.
- Starting a conversion schedules `scrollIntoView({ block: 'nearest' })` for the progress card.
- Extra bottom scroll padding and progress scroll margin keep the card above the sticky action footer.

## Problem 2: server admission decision could be bypassed

v1.6.74 added server-side incident admission limits, but the compatibility client treated every Callable failure as eligible for direct Firestore fallback. A deliberate `resource-exhausted` or emergency-disabled response could therefore be stored through the compatibility path.

### Fix

- Same-origin Callable errors preserve structured `details`.
- Rate-limit and emergency-disabled responses are classified as deliberate admission rejections.
- Deliberate rejections are rethrown before direct Firestore fallback.
- The incident reporter marks those outcomes as suppressed and does not add a new local retry queue entry.
- Network, deployment, and compatibility failures continue to use the existing Firestore fallback behavior.

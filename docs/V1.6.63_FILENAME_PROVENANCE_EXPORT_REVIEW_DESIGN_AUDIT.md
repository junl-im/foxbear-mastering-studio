# v1.6.63 Filename Provenance, Export Review, and Design Audit

## Scope

This release audits filename correctness after v1.6.61-v1.6.62, with emphasis on hidden stale state, 1,000-track behavior, Unicode boundaries, clipboard restrictions, accessibility, and narrow-screen layout.

## Applied changes

1. `sourceFileName` is captured when the track model is created.
2. `outputNameMeta.sourceName` is frozen when mastering completes.
3. Filename generation prefers mastering-time source provenance over later mutable labels.
4. Bulk summary cache keys hash every completed track and all filename-affecting metadata.
5. The export panel shows a bounded 12-name review and copies the complete final list.
6. ZIP preflight identifies collision, sanitization, and byte-limit truncation adjustments.
7. UTF-8 truncation uses `Intl.Segmenter` grapheme clusters when available and a safe code-point fallback.
8. Download filename copy has visible and screen-reader status feedback.
9. Mobile filename actions use a two-button full-width layout with 44 px targets.
10. Forced-colors borders preserve control boundaries.

## Challenge questions and answers

1. **Can a middle completed row change without refreshing the summary?** No. Every completed row contributes to the summary hash.
2. **Can count and last row stay identical while the preview is stale?** That former failure mode is covered by the new regression.
3. **Can a later UI rename rewrite an old master filename?** No. Mastering-time `sourceName` is frozen.
4. **What about old tracks without `sourceFileName`?** The workflow falls back to `track.name`.
5. **What about old completed tracks without `outputNameMeta.sourceName`?** It falls back to `sourceFileName`, then `name`.
6. **Can 1,000 results create 1,000 preview nodes?** No. The visible review is capped at 12.
7. **Can users still inspect all 1,000 names?** Yes. The complete newline-separated manifest can be copied.
8. **Does copying change the export plan?** No. It reads the same finalized plan used by ZIP naming.
9. **Can clipboard denial block downloads?** No. It only reports a recoverable copy failure.
10. **Can a duplicate disappear from the warning count?** No. Collision count comes from finalized unique-name planning.
11. **Are sanitized names distinguished from collisions?** Yes. Adjustment records carry `sanitizedChanged` and `collision`.
12. **Are overlong names distinguishable?** Yes. Adjustment records carry `truncated`.
13. **Can the filename exceed 240 UTF-8 bytes after adding ` (2)`?** No. Duplicate suffix budgeting re-truncates the stem.
14. **Can an emoji family be cut after a zero-width joiner?** Grapheme segmentation avoids it; fallback cleanup removes dangling joiners.
15. **Can a combining mark be left alone at the end?** Trailing combining ranges are removed after fallback truncation.
16. **Can a variation selector be left dangling?** It is removed if it would terminate a truncated fallback.
17. **Is Korean normalization stable?** Names are normalized to NFC before sanitization.
18. **Are Windows reserved names still protected?** Yes.
19. **Are trailing spaces and periods still removed?** Yes.
20. **Are filesystem-forbidden characters still replaced rather than deleting the surrounding words?** Yes, they become collapsed spaces.
21. **Can the copy button keep stale text after format selection changes?** The preview is rebuilt from the current selected format before copying.
22. **Can copy success remain visible after the preview changes?** No. Preview updates clear the old copy status.
23. **Can copy remain disabled forever during an export?** Busy-state release re-enables it; the copy timer also restores it when no action is active.
24. **Can the settings and copy buttons overlap at 360 px?** They become a two-column full-width action grid.
25. **What if translated labels become longer?** Buttons wrap and the action container permits wrapping.
26. **Can the export review widen the console?** Every container uses `min-width: 0` and filename text wraps anywhere.
27. **Can the review make the console indefinitely tall?** The list has a bounded viewport-relative maximum height and internal scrolling.
28. **Can nested scrolling propagate into the page unexpectedly?** The review list uses `overscroll-behavior: contain`.
29. **Can keyboard users open the review?** Native `details/summary` behavior is retained with a visible focus ring.
30. **Can screen readers hear copy status?** Both direct and manifest copy statuses use polite live regions.
31. **Can forced-colors mode lose card boundaries?** Explicit `CanvasText` borders are applied.
32. **Does reduced-motion behavior remain safe?** No new required motion was added.
33. **Can a missing export guard crash the summary?** The workflow falls back to completed-track names.
34. **Can an export-plan exception poison the cache key?** The DOM cache key is committed only after successful rendering.
35. **Can the full manifest order differ from ZIP order?** Both use the same `plan.files` order.
36. **Can format preferences update only the direct download name?** Existing v1.6.62 refresh still updates completed outputs and bulk preflight.
37. **Can localStorage failure lose the filename switches?** The v1.6.62 session-memory fallback remains.
38. **Can a title containing metadata-like words be preserved explicitly?** The policy exposes `preserveExactTitle` for callers that know the title is authoritative.
39. **Can generated legacy suffix cleanup still work?** Existing full and partial legacy cleanup remains the default for re-import compatibility.
40. **Is real-device verification complete?** No. Desktop/mobile/Kakao clipboard and downloaded ZIP comparison remain external acceptance items.

## Design verification

Chromium local and `file:` navigation are blocked by container policy. The audit therefore starts Chromium with the DevTools Protocol, injects the actual CSS and representative DOM using `Page.setDocumentContent`, and captures 360x800, 430x932, and 1280x900 layouts. All three reported viewport-equal scroll width with no horizontal overflow. The 12-row review remained internally scroll-bounded and the 360 px filename actions remained fully visible.

## Known limitations

- Browser filename APIs cannot reliably infer whether metadata-like words at the end of a newly imported filename are part of the artistic title or a previous generated suffix.
- Clipboard APIs may be denied inside in-app browsers; the user receives a failure message and can continue exporting.
- Real downloaded filenames and ZIP extraction behavior still require Windows, macOS, Android, iOS, and KakaoTalk acceptance.

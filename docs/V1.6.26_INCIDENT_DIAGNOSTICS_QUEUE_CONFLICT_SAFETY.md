# v1.6.26 Incident Diagnostics and Queue Conflict Safety

## Scope

This patch separates incident-service failure classification and diagnostic UI view-model generation from the main reporter, and replaces direct local queue array writes with a bounded conflict-safe queue store.

## Problems found

1. `flushQueue()` loaded one array snapshot and later overwrote local storage with a remainder derived from that snapshot. A report queued while the flush was active could therefore be lost.
2. If queue recovery was aborted after one or more successful deliveries, the old implementation left every snapshot entry stored. Already delivered reports could be sent again on the next recovery.
3. Queue metrics used the pre-truncation array length. Adding a ninth unique report could store eight entries while reporting nine remaining entries.
4. Queue parsing, deduplication, item limits, storage quota fallback, and persistence statistics were spread across reporter helpers and could not be stress-tested independently.
5. Firebase service failure classification and all seven diagnostic UI rows were embedded in `incident-reporter.js`, increasing coupling between transport diagnosis, state mutation, and DOM rendering.

## Changes

### `incident-local-queue-service.js`

- Owns parsing, validation, fingerprint deduplication, eight-item retention, and a 96 KiB serialized storage budget.
- Rejects malformed and unexpectedly oversized stored values without exposing report contents in diagnostics.
- On storage quota failure, progressively removes the oldest entries and retains the newest reports that can be persisted.
- Exposes snapshot and fingerprint-removal operations. Flush commits reload the latest stored queue and remove only successfully delivered fingerprints, preserving entries added after the snapshot.
- Tracks metadata-only counters for parse errors, oversized loads, storage failures, dropped entries, duplicate skips, and conflict-safe commits.

### `incident-service-diagnostics.js`

- Owns offline, missing deployment, CSP/network block, CORS response block, and reachable internal-error classification.
- Produces immutable view models for service version, Callable name, endpoint, Hosting same-origin fallback, direct probe, CSP, and App Check rows.
- Keeps the reporter responsible only for collecting runtime inputs, applying the view model to DOM nodes, and mutating incident state.

### Reporter integration

- Queue recovery uses a store snapshot and commits delivered fingerprints against the current queue.
- Successful items are removed even when a later item fails or an AbortSignal interrupts the recovery.
- Newly queued reports survive an active flush.
- Queue metrics use the actual persisted count.
- Anonymous diagnostics include queue storage counters and limits, never report text, stack data, audio, filenames, tokens, or paths.

## Regression contract

`qa/v1626_incident_diagnostics_queue_conflict_safety_smoke.js` verifies:

- 50 enqueue attempts remain bounded to the newest eight entries.
- duplicate fingerprints do not grow the queue.
- quota fallback retains the newest entries.
- malformed and oversized storage fail safely.
- a report added after a flush snapshot survives the delivered-item commit.
- service failure classification precedence and all major UI view-model states.
- runtime script order, service-worker caching, handoff inclusion, and removal of the stale snapshot overwrite path.

## Unchanged contracts

- Audio DSP, mastering loudness and peak targets, encoders, download formats, Firebase document schema, SMTP payloads, and report contents are unchanged.
- Production Firebase, App Check enforcement, Gmail receipt, installed-browser behavior, and real-device lifecycle/network behavior remain environment-dependent release gates.

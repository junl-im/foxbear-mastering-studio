# v1.6.25 Incident Recovery Timeout, Abort, and Trigger-Storm Hardening

## Scope

- Move automatic service-recovery timer, retry-budget, and execution ownership out of `incident-reporter.js`.
- Add phase-specific service, queue, and deployment deadlines with a shared abort signal.
- Preserve bounded 5/15/45-second retry behavior without losing retries while an active run is cleaning up.
- Prevent offline periods, hidden settings surfaces, and repeated network triggers from wasting retry budget or spawning duplicate work.

## Confirmed problems

1. A failed automatic recovery attempted to schedule its next retry from inside the active Promise catch path. Because the reporter still marked recovery as in flight, the scheduler rejected the request and the documented multi-attempt sequence could stop after one run.
2. Offline timers could consume retry attempts even though no network phase could succeed.
3. Service, queue, and deployment phases had no common deadline or cancellation signal. A stalled Promise could keep the recovery UI and ownership state active indefinitely.
4. Late completions after a timeout could still mutate reporter state because the underlying callbacks did not observe a shared abort signal.
5. Repeated connection or visibility triggers needed a deterministic stress contract proving one active run and one scheduled timer.

## Changes

- Added `src/boot/incident-service-recovery-controller.js` as the owner of retry timers, attempt budget, active task, phase deadlines, abort propagation, slow-phase diagnostics, offline waiting, hidden-surface suspension, result snapshots, and disposal.
- Retry scheduling after a failed run is deferred until active ownership is cleared.
- Offline failures enter `waitingForOnline` without creating timers or consuming attempts.
- Hidden recovery surfaces suspend the scheduled retry and reset the unused attempt budget.
- Service, queue, and deployment callbacks receive one AbortSignal. Reporter bridge waits, service probes, queue delivery, and deployment checks reject aborts before applying late state mutations.
- Anonymous diagnostics expose only bounded recovery timing metadata: timeout count, abort count, last timed-out phase, and slow phase names.
- The reporter keeps a small compatibility fallback for isolated historical VM fixtures, while production loading and package verification require the dedicated controller.

## Default deadlines

- Service health recovery: 22 seconds.
- Local queue flush: 30 seconds.
- Deployment readiness: 45 seconds.
- Slow-phase diagnostic threshold: 4 seconds.

## Compatibility

- Incident payloads, Firestore schema, Functions endpoints, SMTP content, Firebase route policy, audio DSP, mastering targets, encoders, and download formats are unchanged.
- Existing public reporter methods `runServiceAutoRecovery`, `scheduleServiceRecovery`, and `clearServiceRecoveryTimer` remain available.
- The retry delay sequence remains 5, 15, and 45 seconds.

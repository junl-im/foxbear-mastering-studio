# v1.6.32 Overlay History Generation and BFCache Recovery

## Problem

The v1.6.31 transaction flag coalesced rapid internal Back requests, but a delayed `popstate` still lacked an identity. A newer genuine user Back could therefore be mistaken for the pending internal cleanup. BFCache could also restore after the history traversal completed but before its `popstate` listener ran.

## Change

- Each base history entry and overlay sentinel share a positive generation number.
- `isInternalHistoryReleaseEvent(event)` classifies only the exact destination generation or a short-lived pending generation.
- A mismatched event abandons the active release and continues through the normal overlay or workspace Back path.
- A late exact event is absorbed as stale internal cleanup without reopening the exit confirmation.
- `pagehide` suspends the release watchdog. Persisted `pageshow` reconciles the current state, settles completed releases, retries untouched sentinels, or abandons mismatched state.
- The navigation exit guard recognizes an already-current exit guard or overlay sentinel during BFCache restoration and avoids duplicate `pushState`.

## Compatibility

Browsers with `replaceState` receive generation fencing. A bounded legacy path remains for older test or embedded contexts that provide only `pushState`, preserving the previous one-sentinel overlay behavior.

## Privacy

Diagnostics contain only counters, booleans, and generation numbers. They do not contain URL history, filenames, audio, incident text, credentials, or user identity.

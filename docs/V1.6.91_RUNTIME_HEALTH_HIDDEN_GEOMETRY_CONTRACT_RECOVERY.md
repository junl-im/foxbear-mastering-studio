# v1.6.91 Runtime Health hidden-element geometry contract recovery

## Failure decoded

GitHub Actions repeatedly rendered `Expected: <= 1` / `Received: 91.96875` inside the mobile Runtime Health test. That output was previously interpreted as the strict `rowOverlap <= 1px` assertion, but the current test source would throw `FOXBEAR_HEADER_OVERLAP_*` before that assertion if overlap were actually greater than one pixel.

The failing assertion occurred earlier. At widths of 430px and below, `.brand-command-studio` is intentionally `display:none`. A hidden element returns a zero DOMRect, so `studioLeft` becomes `0`. Runtime Health nevertheless asserted `deviceRight <= studioLeft + 1`, producing an expected maximum of `1` and a received visible-device coordinate near `91.96875` in CI.

## Recovery

Runtime Health now derives whether Studio has visible geometry. When visible, it retains the normal `device → studio → actions` ordering checks. When hidden, it compares the last visible left token (`deviceRight`) directly against `actionsLeft`. The strict `rowOverlap <= 1px` assertion remains unchanged.

The production `header-command-bar.css` is intentionally unchanged. Its `flex-two-rail-v1690` contract remains the active layout generation marker.

## Diagnostic improvement

Each ordering assertion now carries a relation-specific message. A future failure will identify whether the problem is `build→device`, `device→studio`, `studio→actions`, or compact `device→actions`, preventing a generic `Expected <= 1` message from being mistaken for row overlap.

## Verification

The full configured static/behavioral suite passes 447/447. A Pixel-class Chromium reconstruction using the same 27 stylesheet load order reports zero left/right rail overlap at both 393px and 320px. Engine QA, golden audio, and piano transient checks remain unchanged and passing.

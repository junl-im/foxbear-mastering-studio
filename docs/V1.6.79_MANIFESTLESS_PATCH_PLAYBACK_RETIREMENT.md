# v1.6.79 Manifestless Patch Delivery and Bounded Playback Retirement

## Why this patch exists

A GitHub Actions run reported `Source hygiene auto-repair: PATCH_MANIFEST.json`. The annotation itself is a warning from the `ci-safe` cleanup path, not the fatal exit by itself, but it exposed an avoidable delivery problem: the overwrite ZIP extracted a generated manifest into the repository root and then asked the user to delete it.

## Delivery change

- Changed-file patch ZIPs no longer contain `PATCH_MANIFEST.json`.
- `DELETE_PATHS.txt` still lists `PATCH_MANIFEST.json` so older extracted/committed manifests are removed during upgrade.
- Source hygiene now treats a legacy root manifest as forbidden generated state.
- Patch verification checks archive safety, release generation, required handoff files, and—when Git metadata is available—the exact expected Git diff, without generating repository-root metadata.
- The CI-safe hygiene fixture verifies that a legacy manifest emits cleanup behavior and does not itself cause the release gate to fail after removal.

## Playback resource change

The playback recovery service already declared a 45-second retirement maximum but did not enforce it. A stale paused `<audio>` element could therefore retain an obsolete mastered Blob URL indefinitely.

- Retired URLs remain protected while actively playing.
- Once the 45-second retirement deadline has elapsed, an inactive paused/ended stale reference can be revoked.
- If playback remains active beyond the deadline, retirement waits until playback stops.
- Explicit track release still forces immediate cleanup.

`qa/v1679_manifestless_patch_playback_retirement_smoke.js` covers manifestless delivery, strict/ci-safe hygiene behavior, and inactive-versus-active playback retirement.

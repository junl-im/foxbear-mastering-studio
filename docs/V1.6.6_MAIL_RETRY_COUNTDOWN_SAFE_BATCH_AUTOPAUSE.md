# v1.6.6 Mail Retry Countdown and Performance-Safe Batch Auto-Pause

## Problem

Manual mail tests exposed the final failure reason but did not make the retry schedule or attempt count visible. Users also had no safe non-admin path to retry their own failed test after correcting SMTP deployment or credential settings. Separately, the performance monitor could warn about a dangerous condition while a multi-track mastering batch continued starting new tracks.

## Mail retry contract

- Local history stores only bounded diagnostic metadata: report ID, Message-ID, status, attempt count, next retry timestamp, and direct retry count.
- `retryOwnIncidentReport` requires Firebase anonymous authentication and a report ID owned by the current UID.
- Only `manual-test` reports with `automatic=false`, `delivery.status=failed`, and `terminal=false` may be retried.
- Already emailed, pending, automatic, foreign, dead-letter, and terminal reports are rejected.
- Direct retries are limited to two per report with a 60-second server-side cooldown.
- Automatic retry scheduling remains available and is shown as a human-readable countdown.

## Performance protection contract

- The batch runner listens to the confirmed ambient performance-health event.
- A danger state marks the batch as auto-paused. The current track is allowed to finish, but the next track cannot start.
- Manual resume is rejected while the batch is auto-paused for performance protection.
- Only a confirmed normal state releases the pause and resumes the remaining queue.
- A manually paused batch is never auto-resumed by health recovery.

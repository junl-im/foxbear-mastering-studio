# v1.6.29 Incident Submission Fencing, Adaptive Polling, and Controls Isolation

## Scope

This patch hardens delayed anonymous incident recovery across browser tabs. It gives each incident occurrence one stable server identity, fences stale queue owners by lease generation, reduces fallback synchronization work in idle and hidden tabs, and moves primary incident-setting DOM responsibilities out of the main reporter.

## System and data-integrity changes

- `incident-submission-identity-service.js` derives a stable `submissionKey` from the incident fingerprint and its original client timestamp.
- The same key follows the occurrence through local queue storage, Callable delivery, Hosting same-origin delivery, and Firestore compatibility delivery.
- Firebase client and Functions report IDs no longer depend on the retry-time 15-minute window, preventing a delayed retry from creating a second server document for the same occurrence.
- Callable and Firestore acknowledgements return the submission key. The reporter rejects a mismatched acknowledgement before removing the local queue entry.
- Firestore rules explicitly allow and validate the bounded submission key.

## Cross-tab ownership fencing

- Local-storage lease ownership now includes a monotonically increasing generation in addition to its token.
- A token match is insufficient when the generation differs; storage events, heartbeat checks, expiry checks, and explicit owner checks abort stale work.
- Queue delivery passes the active generation into transport diagnostics and validates ownership around each network submission and local commit.
- Post-claim verification requires token, generation, and unexpired TTL.
- Cleanup removes a lease only when both token and generation still match. An older tab therefore cannot delete a replacement generation during `finally` or lifecycle release.

## Adaptive fallback synchronization

- Visible tabs with queued work use the active fallback cadence.
- Visible tabs with an empty queue use a slower idle cadence.
- Hidden tabs use the slowest cadence.
- Returning to the foreground schedules an immediate resynchronization before selecting the next cadence.
- Polling timers are recursively scheduled, rescheduled when queue/visibility state changes, and fully cleared on disposal.
- Environments without the required timer capability do not create a fallback timer that can keep non-browser VM processes alive.

## UI responsibility split

`src/boot/incident-controls-view-service.js` now owns:

- collection of the primary incident-setting controls,
- busy and disabled-state rendering,
- recovery and deployment status presentation,
- one-time event binding,
- bounded transient button feedback.

`incident-reporter.js` retains workflow and state orchestration while delegating those DOM responsibilities to the controls view.

## Problems fixed

- Delayed recovery after a time-bucket boundary could generate a new report ID for the same queued occurrence.
- A stale acknowledgement could otherwise be committed without proving that it belonged to the current local occurrence.
- A same-token generation replacement could abort the old tab but still be deleted by that tab's cleanup path.
- Empty visible tabs and hidden tabs continued using the same two-second polling cadence as active queues.
- Two new boot modules were initially absent from the service-worker atomic install graph; the release gate detected this and the modules are now included in the precache contract.
- A historical popup QA assertion depended on the old source-file location of the busy-state implementation; it now verifies the delegated controls-view contract.

## Performance and engine impact

- No DSP, mastering target, analyzer, limiter, encoder, download-format, audio-worker, or recommendation algorithm was changed.
- Adaptive polling lowers idle and background coordination wakeups while preserving immediate foreground recovery.
- The final synthetic mastering regression reported approximately `1.82x` realtime.
- All four golden-audio fixtures retained `-14.00 LUFS`; peak values remained between `-9.62` and `-5.64 dBTP`, and the peak-stress contract remained `-1.00 dBTP`.

## Privacy and compatibility

The stable submission key is a bounded local identifier derived from an already-sanitized fingerprint and client timestamp. This patch does not add audio, filenames, full paths, report text, stack traces, credentials, tokens, IP addresses, SSIDs, location, or raw tab identifiers to diagnostics. Existing SMTP content and Firebase incident fields remain compatible except for the additive validated `submissionKey`.

# v1.6.30 Overlay History Release and Exit Guard Safety

## Summary

Some dialogs add one temporary browser-history entry so the browser Back action closes the top dialog before leaving the studio. When a dialog was closed normally, the modal controller removed that temporary entry with an internal `history.back()` call.

The navigation exit guard could receive that internal `popstate` before the modal controller marked it as consumed. With meaningful workspace state present, the internal cleanup was therefore occasionally mistaken for a real user Back action and could show the leave-confirmation message or the cancellation toast.

## Root cause

- The navigation exit guard is installed during application initialization.
- The modal history listener is installed only when the first eligible dialog opens.
- Listener registration order therefore commonly places the exit guard before the modal listener.
- Programmatic sentinel release happened after the last dialog closed, so the exit guard observed no open overlay.
- The modal controller marked every `popstate` as overlay-handled only when its later listener ran.
- This created an event-order race between legitimate internal cleanup and genuine browser navigation.

## Changes

- Exposes modal sentinel-release state through `isHistoryReleaseInFlight()`.
- Makes the exit guard ignore a `popstate` while the modal controller is releasing its own sentinel.
- Marks `foxbearOverlayHandled` only when the modal controller actually consumes an internal release or closes an open dialog.
- Leaves genuine Back events unmarked when no overlay is open, regardless of listener installation order.
- Adds an integrated VM regression with the real application listener order: exit guard first, modal listener second.

## Privacy and functional scope

This patch changes only client-side history coordination. It does not change audio processing, mastering settings, exports, Firebase schemas, incident payloads, SMTP behavior, authentication, or stored user content.

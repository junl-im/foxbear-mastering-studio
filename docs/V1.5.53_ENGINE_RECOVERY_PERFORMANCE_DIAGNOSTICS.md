# FoxBear v1.5.53 Audit and Patch Report

## Confirmed runtime failure

The packaged `vendor/jszip/jszip.min.js` file exists and its SHA-384 SRI digest matches `index.html`. The load failure was caused by service-worker generation routing, not by a missing or corrupted vendor file.

`sw.js` treats the `v` query parameter as the application asset generation. JSZip was requested as `?v=3.10.1`, so the current service worker classified it as a legacy application generation and returned `Response.error()` before normal loading. The browser then reported `load-error-or-sri-block`.

The corrected URL is:

```text
vendor/jszip/jszip.min.js?v=1.5.53-engine-recovery-performance-diagnostics&lib=3.10.1
```

The application generation and library version now have separate meanings. The same URL contract is applied to `index.html`, the service-worker precache, and `zip-encoder.worker.js`.

## Handoff audit

The v1.5.52 handoff covered CI parallelization but did not document the planned engine recovery or full per-track performance UI. Existing code already collected total and stage timings, but the UI exposed only a partial summary. There was no automatic safe rerender after a quality-gate failure.

A separate release issue was also found: `foxbear-root.json` still declared v1.5.49 while the package declared v1.5.52. The metadata synchronizer now writes and validates the root marker.

## Implemented engine recovery

When the final quality gate returns `FAIL`, the orchestrator creates a conservative plan and the engine performs at most one additional render from the already prepared source buffer. The safe plan reduces high-risk width, punch, clarity, groove, and intensity; uses bounded fast finalization; enables True Peak; lowers the ceiling; and reduces loudness pressure when the failure indicates clipping, limiting, pumping, or loudness risk.

The retry recomputes finalization, encoding, master report, quality gate, comparison, waveform, A/B highlight, safety information, True Peak telemetry, and export fallback state.

### Exception rules

- A passing or warning gate does not trigger recovery.
- A track already marked as attempted cannot retry again.
- A second quality-gate failure is recorded as `failed-after-retry` and completes without a retry loop.
- Cancellation/job ownership checks run after each expensive retry stage.
- If retry rendering, finalization, or encoding throws, the original settings and performance guard are restored and the first valid output remains the active result.
- An empty or invalid retry Blob is treated as a recovery error, not as a replacement output.

## Implemented performance diagnostics

The selected-track detail screen now shows:

- total DSP processing time
- slowest DSP stage and duration
- real-time processing speed (`audio duration / processing duration`)
- finalizer processing time
- every recorded DSP stage with a relative timing bar
- quality recovery status

The hidden runtime diagnostics panel also includes the selected-track summary through `FoxBearMasteringDiagnostics.getSnapshot()`.

## Remaining considerations

- Safe settings are deterministic and intentionally conservative; future tuning can map more individual quality flags to specialized recovery profiles.
- Browser QA should force both a successful recovery and an injected recovery exception with real AudioBuffers.
- Very short tracks can produce unstable real-time ratios; the UI handles missing/zero values as “calculation pending.”
- Timing values use wall-clock measurements and are diagnostic, not a hardware benchmark guarantee.
- Users with a previously active service worker may need one normal reload for v1.5.53 activation; the corrected generation prevents the JSZip false rejection after activation.

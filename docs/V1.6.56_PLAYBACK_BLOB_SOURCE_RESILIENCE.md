# v1.6.56 Playback Blob Source Resilience

## Problem

Mobile browsers and embedded WebViews can discard or invalidate an `audio` element's Blob URL while the retained source File or result Blob is still available. The Dock previously marked the player as failed but did not recreate the media URL. Re-mastering also revoked the previous mastered URL immediately, which could interrupt a player that still owned that source during the completion transition.

## Changes

- Added `src/audio/playback-source-recovery-service.js`.
- Recreates original playback from `track.file`.
- Recreates mastered playback from `track.outBlob`.
- Recreates highlight playback from `track.masterPreviewBlob`.
- Preserves the current playback position during source repair.
- Resumes only when the latest playback intent still requests playback.
- Limits recovery to two attempts in a 15-second window and shares an in-flight repair per audio element.
- Defers Object URL revocation while any connected audio element still owns the URL.
- Force-releases deferred URLs when the track is removed.
- Keeps an immediate-revoke fallback when the recovery service is unavailable.
- Restores a remembered audible volume when playback is active, no fade is running, and volume is stuck near zero.
- Prevents native pause reconciliation from clearing intent while a source repair is pending.

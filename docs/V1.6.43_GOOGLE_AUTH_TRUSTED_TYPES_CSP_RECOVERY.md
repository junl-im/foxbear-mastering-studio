# v1.6.43 Google Auth Trusted Types and CSP Recovery

## Symptom

Selecting **Google 계정으로 인증** from administrator monitoring failed before the account chooser opened with:

`Failed to execute 'setAttribute' on 'Element': This document requires 'TrustedScriptURL' assignment.`

## Root cause

The production page enforces `require-trusted-types-for 'script'` and previously allowed only the application-owned `foxbear` policy. Firebase Auth loads the Google API iframe helper by assigning `https://apis.google.com/js/api.js?...` to a script element internally. That library cannot access the private FoxBear policy, so Chromium rejected the plain string at the TrustedScriptURL sink. The Firebase Hosting response CSP also omitted part of the Google Auth script/frame allowlist and used a popup-isolating COOP value.

## Recovery

- Add an early `src/security/trusted-types-bootstrap.js` before Firebase initialization.
- Register a narrowly validated Trusted Types `default` policy.
- Allow only:
  - the exact Firebase Auth Google API loader path,
  - existing Google reCAPTCHA script paths,
  - FoxBear same-origin `/src/` and `/vendor/` scripts.
- Reject other origins, other `apis.google.com` paths, and arbitrary same-origin upload paths.
- Align both the document CSP and Firebase Hosting header CSP.
- Use `Cross-Origin-Opener-Policy: same-origin-allow-popups` for the account chooser.
- Precache the bootstrap with the current service-worker generation.
- Normalize stale cached-policy errors into a Korean refresh instruction.

## Regression

`node qa/v1643_google_auth_trusted_types_csp_recovery_smoke.js`

The regression checks policy order, exact host/path validation, CSP parity, popup COOP, service-worker precache, and rejection of untrusted script URLs.
